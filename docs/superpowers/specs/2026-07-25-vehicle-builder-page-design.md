# Vehicle builder page (`/build`) — design

Date: 2026-07-25. Status: designed autonomously from the user's spoken spec;
decisions the user did not dictate are marked **(choice)** with the reasoning.

## What the user asked for

> Create a new /launcher or /build page that takes what you have in the
> launcher section right now, brings it in, and shows the vehicle there. You
> can add and remove stages, and it gets updated and shown. You can add and
> remove the strap-on boosters to the side and do that dynamically. You can
> dynamically update the diameter stages or see what the model will actually
> look like for it and other important aspects of it. Also, make sure that
> engines only work with their corresponding fuel mixture, so a Raptor
> methalox engine doesn't work with a kerolox mixture. You should essentially
> give it a launcher section on the main page, and that should just be its own
> kind of separate configuration window with the model in the center and then
> different statistics and parameters on the left and right sides.

## What already exists (found by exploration)

- The panel page (`/`) has a **Launcher card** (`panel_page.html:190-220`)
  with `nstages` (2–5), `nboost` (0/2/3/4/6), `fairing`, `diameter`,
  `kick_deg`, and per-stage blocks generated by `buildStages()` with fields
  `s{k}_{size_by,diameter,prop,len,dry,engines,dry_auto,thrust_kn,isp,
  propellant,engine}` plus a `b_*` strap-on set with `throttle`, `ign_delay`,
  `sep_delay`.
- **`POST /api/geometry`** (`panelapp.jl:643-709`) already returns everything
  a builder needs from the same form encoding: the authoritative mesh
  (`tris`, flat 9-float triangles, +x = nose, metres; `sections` with
  1-based inclusive triangle ranges named `stage1..K`, `pod`, `glass`,
  `cabin`, `fairing`, `booster1..M`), per-stage stats (`dv_mps`, `twr`,
  `burn_s`, `length_m`, `volume_m3`, `interstage_m`), booster-set stats, and
  vehicle totals (`length`, `liftoff_mass_kg`, `liftoff_twr`,
  `total_dv_mps`).
- `/api/catalogue` returns the engine table with each engine's `propellant`,
  and the propellant table with bulk densities.
- **No engine↔mixture validation exists anywhere.** The engine silently
  overrides the mixture (`panelapp.jl:115-116`, `config.jl:36-53`), and the
  panel's "hydrolox upper" preset (`panel_page.html:716-719`) visibly ships
  that bug: form says kerolox, server flies hydrolox.
- Navigation pattern: the panel's `launchbtn` chip does
  `window.open('/launch?' + params(), '_blank')`; the launch page rehydrates
  by replaying `location.search` as a POST body. Pages are single
  self-contained HTML files; there is no static-asset route.

## Design

### Route and file

`GET /build` serves a new single-file `scripts/build_page.html`, via a
`BUILD_PATH` Ref beside `PAGE_PATH`/`LAUNCH_PATH` and one route branch —
identical pattern to `/launch`, re-read per request. **(choice)** Name is
`/build` (user offered either; shorter, and "launcher" stays the name of the
panel card).

### Page layout

Three columns, dark theme matching the existing pages:

- **Center:** a WebGL canvas showing the assembled vehicle from
  `/api/geometry`'s `tris`, lit, per-section tinted (stages alternating hull
  shades, fairing distinct, boosters distinct), slow auto-rotation, drag to
  orbit, wheel to zoom, with a 10 m scale reference. Falls back to a clear
  error banner if WebGL is unavailable.
- **Left: configuration.** Vehicle row (name, diameter, fairing, payload
  mass), a **stage list** with per-stage cards and `+ add stage` / `remove`
  controls (server range 2–5), and a **strap-on booster** card with count
  0–8, the `b_*` fields, and add/remove. Cards carry the same field ids and
  encoding as the panel so the query string is interchangeable.
- **Right: statistics.** Vehicle totals (length, liftoff mass, pad T/W with
  the existing verdict thresholds — <1.15 "will not lift off", <1.25
  "sluggish" — total Δv with the <11500 m/s "thin for a Moon shot" note),
  a per-stage table (prop, dry, length, Δv, T/W, burn, interstage), booster
  set line, and two derived numbers the server doesn't send but the page can
  compute: **payload fraction** and per-stage **mass ratio**.

Data flow: any input change → debounced (~150 ms) POST of the form encoding
to `/api/geometry` → stats re-render + mesh rebuild. No mission is flown.

### Add/remove semantics

`+ add stage` inserts before the kick stage with the role defaults the panel
already uses (`stage_scale` mirroring); `remove` on a card decrements
`nstages` and drops that card's values, re-labelling roles (stage 1 =
booster, last = kick). Booster count is a stepper 0–8; 0 hides the card
body. All rebuilds preserve typed values by id, the way `buildStages()`
does.

### Engine ↔ mixture compatibility (the new rule)

- **Server (authoritative):** in `stage_from_params` (`panelapp.jl:115`),
  when a named engine is chosen AND the form supplies a non-empty
  propellant that differs from the engine's, return the standard
  `{ok:false, error:"raptor_2 burns methalox; it cannot run on kerolox"}`
  instead of silently overriding. Manual mode keeps free choice of mixture.
- **Builder UI:** selecting an engine locks the mixture select to that
  engine's propellant (shown, disabled, labelled "set by engine"); switching
  back to manual unlocks it. The engine dropdown groups options by
  propellant so the coupling is visible.
- **Panel page:** same lock applied to its existing dropdowns (small JS
  addition in `syncSizeBy`), and the "hydrolox upper" preset gains
  `s2_propellant: 'hydrolox'` so nothing ships a mismatch. This is required —
  with server validation on, the panel would otherwise 200/error on a preset.

### Navigation ("launcher section on the main page")

- Panel Launcher card header gains a chip: `🛠 vehicle builder`, opening
  `/build?' + params()` in a new tab (mirrors `launchbtn`), key `B`, and a
  Keys-card row.
- `/build` rehydrates every field from `location.search` on load, then
  fetches geometry.
- `/build` has: `↩ mission control` backlink (`/?` + current params — see
  below) and a `🚀 launch view` chip (`/launch?` + params + `mode=flyby`) so
  a built vehicle can be flown immediately.
- **(choice)** To make the round trip real, the panel page learns to
  rehydrate its form fields from `location.search` (it already does this for
  `mode` and `zoom`): set `nstages`/`nboost` first, `buildStages()`, then
  fill the rest, then `fetchGeo()`. This reuses the `applyPreset` machinery.

### Testing

- `test/panel_http.jl` additions: `GET /build` returns 200 + HTML;
  mixture-mismatch POST to `/api/geometry` returns `ok:false` with the
  engine and both propellant names in the error; matched pair still `ok`;
  manual mode with any mixture still `ok`.
- Julia-side unit test for the new validation function.
- Builder page carries a small `?selftest=1` console suite for its pure
  helpers (form encode/decode, payload fraction, mass ratio), matching the
  launch page's pattern.

### Out of scope (YAGNI)

Multiple booster sets (model supports it; panel and builder expose one set —
matching the server's single-set parser), TOML export, saving named designs,
`ae`/throttle_min editing, drag-to-reorder stages.
